| A-22 (BPMS-081) | Expression engine, as built (docs/11 §6.1). (1) **Our own CEL-subset implementation** (parser, type checker, evaluator) instead of `cel-rust`. `cel-rust` has no step budget (only the non-deterministic wall-clock guard SP-08 suggested, and `wasm32` has no clock), uses IEEE doubles, and has no static checker. Our implementation follows CEL syntax and precedence, so it is a CEL subset, not the custom DSL ADR-0010 rejects. (2) There is no floating point: `1.5` is an exact decimal, and an integer is accepted wherever a decimal is. (3) `&&`/`||` short-circuit left to right; CEL's commutative error absorption is not implemented. (4) Fields of inline `record` types are required. The built-in shapes are principal (`id`, `manager?`, `department?`, `email?`), group (`id`, `name?`), file (`name`, `hash`, `size`, `content_type?`) and instance (`id`, `display_id`, `started_at`). (5) `today()` and date parts use a fixed UTC offset that the caller injects, resolved from the process calendar at `now`; there is no IANA zone database in the engine. (6) Rounding is half away from zero. (7) Event-facing contexts (notify templates, values copied into events, idempotency keys) reject `restricted` reads; confidential reads are allowed and the result carries the classification. (8) Budget defaults: 10 000 steps, 1 MiB allocation, 64 KiB strings, 10 000-element lists, evaluator depth 64. The step budget replaces SP-08's 10 ms wall-clock guard | Owner and architect review at G1 alongside ADR-0010; designer feedback on the language (BPMS-100/101) | Amend ADR-0010 to name the engine explicitly; adopt `cel-rust` if it gains budgets, decimals and a checker; add an IANA zone database behind the calendar port |
| A-23 (BPMS-082) | Native interpreter (docs/11 §15): (1) `set` evaluates every expression against the variables as they were before the node (parallel assignment). (2) A rule-table decision whose output is null or names no branch takes `default`; an expression branch whose condition is not a boolean raises incident IR-R002 (docs/11 §6). (3) Runtime incident codes besides IR-R010: IR-R001 expression failed, IR-R002 non-boolean condition, IR-R003 no edge for an outcome without `unhandled: fail`, IR-R004 loop guard, IR-R005 join outside its split, IR-R006 bad value (timer instant, idempotency key). An incident parks the token; the instance keeps running (docs/04 §4.1 default policy). (4) Loop guard: a node is entered at most `maxIterations` times when it declares one, else 1,000 times per instance; the next entry raises IR-R004. (5) A boundary without `interrupting` interrupts (BPMN default). A non-interrupting boundary token keeps its parent's branch frames; a join counts each branch once. (6) A typed connector error `error:<CODE>` goes to the matching `error:<CODE>` boundary, else to the `error` outcome. (7) Cancelling or terminating withdraws work items, timers, subscriptions and child instances; in-flight connector calls and opened cases are not cancelled, and a late connector result is refused as an unknown key. (8) An outcome produced with no edge and `unhandled: fail` fails the instance. (9) Instance status `terminated` covers both `end{result: terminated}` and an instance cancel (docs/04 stores `cancelled`). (10) Activation and command keys are `<instance>/<node>/<n>` with `n` from the instance's own counter; the connector receives the evaluated `idempotencyKey` separately. (11) Runtime conformance fixtures live in `conformance/runtime/<group>/<case>/` (the repository's conformance crate, docs/04 §1) rather than `crates/runtime/conformance/fixtures/` (docs/15 §4), and the script is `script.json`, not `script.yaml`, to avoid a YAML dependency. Traces are compared in total order, since the native interpreter is deterministic | Runtime-lead review of docs/11 §15; BPMS-083/085/088 integration | Change the parallel-assignment rule; make the loop default 50 (docs/11 §4) for every node; cancel in-flight connector calls; move the fixtures and adopt YAML |

## 5. Explicit non-goals (so they can't creep in)

The following are out of scope:
- Jira-style project management
- payroll/ERP
- full BPMN conformance
- user scripting
- AI auto-approval or people-scoring
- arbitrary-log process discovery
- native mobile apps and offline approvals (before demand gate)
- SCORM/LMS
- payment collection
- certified mass-notification
- real-time co-editing (GA)
- review-sets eDiscovery
- becoming a QTSP/ESP ourselves

Changing any of them requires the change process ([21 §17](21-FEATURE-CATALOGUE.md)).
